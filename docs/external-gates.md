# External gates

This is the complete future launch/activation register of inputs that require
authority, production data, credentials, enrollment, elapsed live operation, or
a decision outside this repository. Fakes and simulators keep implementation and
CI unblocked but can never prove production activation. These inputs do not
block a repository-complete consolidated-main handoff.

Every row below identifies the exact absent input, completed repository control
and deterministic simulator, fail-closed enforcement boundary, and required live
activation test. A `blocked`, `review`, or `pending` launch state describes
external evidence only. Open repository work is tracked as P0-40 through P0-46
in `docs/backlog.md` and never sits behind a gate row.

Operators use `docs/operations/external-gate-activation.md`. `/internal/gates`
must show the owner, configured and effective state, exact absent input, last
activation result, sanitized evidence reference, expiry/review date, row
version, and affected capability. Only current live-signed input plus a
successful live staging activation test may produce `activationAllowed=true`.

## Shared repository enforcement

Every row below uses these completed common controls:

- registry, status/evidence schemas and the capability-to-gate matrix:
  `packages/domain/src/system/external-gates.ts`;
- persisted state, optimistic versions, audit and activation records:
  `packages/db/src/repositories/system/external-gates.ts` and
  `packages/db/src/repositories/system/gate-activation-tasks.ts`;
- MFA-protected system API and generated client contract:
  `packages/api/src/routes/system/external-gates.ts` and
  `apps/web/src/features/contracts/external-gates-client.ts`;
- all-gate deterministic, network-free simulator, which always records
  `repository_fixture` rather than live provenance:
  `packages/api/src/routes/system/external-gate-simulator.ts`;
- durable live activation task with lease fencing, provider-success checkpoint
  and crash recovery: `packages/workflows/src/runtime/gate-activation.ts`;
- last-mile provider denial and production-simulator rejection:
  `packages/integrations/src/runtime/provider-runtime.ts` and
  `packages/integrations/src/runtime/guarded-provider-transport.ts`.

Common enforcement/tests are
`packages/domain/src/system/external-gates.test.ts`,
`packages/api/src/routes/system/external-gate-simulator.test.ts`,
`packages/api/src/routes/system/external-gates.integration.test.ts`,
`packages/db/src/repositories/system/external-gates.integration.test.ts`,
`packages/db/src/repositories/system/gate-activation-tasks.integration.test.ts`,
`packages/workflows/src/runtime/gate-activation.test.ts`, and
`supabase/tests/901_external_gates.test.sql`. A simulator pass is never an
activation pass.

For P0-33 specifically, telemetry instrumentation, correlation, redaction,
exporters, dashboards, alerts, synthetics, runbooks, and tests are complete. Its
`EXTERNAL-ONLY` remainder under `EXT-ACC-01` is limited to selecting the hosted
collector/backend, providing scoped credentials, proving live signal and
primary/backup page delivery, and completing the staging-soak record. Other
`EXT-ACC-01` account inputs gate their own capabilities and are not hidden P0-33
repository work.

## Activation and expiry rule

No gate becomes active because an environment variable exists or a deterministic
suite passes. Activation evidence is append-only and secrets are never
displayed. A missing/expired credential, policy, approval, review date, evidence
object or activation result returns the affected capability to fail-closed
state. Final staging soak, hosted telemetry/page delivery and managed restore
evidence are live release inputs under `EXT-ACC-01`; they are not repository
implementation excuses.
